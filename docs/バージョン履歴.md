## v1.0〜v1.1（2026-07-16〜17）: 店頭スキャン主軸のコンセプト

### 当時のプロジェクト概要（記録として保存）

> 食料品価格の高騰が続くなか、同じ食材でも容量やパック数の違いにより、本当に割安な商品をその場で判断することは難しい。本提案は、スーパーの棚をスマートフォンで撮影するだけで、AIが価格や内容量などを解析し、「100gあたり」などの共通単価に換算して比較を行い、最も安い商品を購入前に提示する買い物支援・食材管理アプリである。また、「できるだけ安く買いたい」「国産品を選びたい」「健康を重視したい」など、利用者が自然な言葉で要望を伝えると、LLMがその意図を理解し、価値観に合った商品を提案する。さらに、購入した食材の賞味期限をスマートフォンで読み取って管理し、期限の近い食材を活用したレシピを提案することで、家計の節約と家庭のフードロス削減を同時に実現する。

### 当時の中核的な考え方

- 存在意義は「**購入前**の意思決定支援」。効果を出したいタイミングと価格が取れるタイミングの一致。
- 差別化は「入力の自動化（撮るだけ）」。単価計算そのものは飽和市場。
- 堀は技術ではなく蓄積データ（個人の買い物台帳・好み学習）。

## v2.0（2026-07-17）: 課題の再定義 — 毎日の献立サイクル全体へ

### 解決する課題（Before）

毎日繰り返される、次の一連の手順のストレスをなくしたい。

1. 冷蔵庫の中をざっと把握して
2. 大体のメニューを考えて、
3. やっと買い物へ。と思ったけど、どのスーパーが安いのか、相場がわからない。
4. お店にて、なるべく安く好みの、足りない食材を頑張って選ぶ。面倒な繰り返し。

### 提供する体験（After）

1. 自分で把握しなくても、冷蔵庫の中身などの**買った食材はすべてアプリで管理**。数量・賞味期限をデータベースで管理。
2. メニューを考えなくても、アプリが**食材を使い切るようにレシピを提案**。無理に既存の食材のみで提案せず、ユーザーの好み寄りのレシピも一緒に提案できる。
3. 作りたいレシピのうち、**足りない食材を買い物リストへ追加**。2日〜5日といった少し先の料理も計画に入れて買い物リストを作成できる。
4. 気になる食材を**ラベル込みでスキャンするだけで、どれを買えばお得かすぐ分かる**。
5. これから作るメニューを確定した時点で、**使う食材と調味料がどれくらい減るかを計算**。
6. 料理後、消費した分量がずれたなと感じても**管理画面から簡単に修正**できる。1から毎日繰り返す。

### v1系から何が変わったか

| 観点 | v1系 | v2.0 |
|---|---|---|
| アプリの主役 | 店頭スキャンによる「購入前の最安提示」 | 在庫DBを土台にした**毎日の献立サイクル全体**（在庫→レシピ→買い物リスト→店頭判定→消費計算→修正） |
| 店頭スキャンの位置づけ | 中核機能そのもの | サイクルの1ステップ（ステップ4）。「買う前に効く」という時間軸の考え方は維持 |
| レシピ提案 | 期限が近い食材の使い切り（付加機能） | 中核機能。在庫消化と**好み寄り提案の両立**（在庫縛りを強制しない） |
| 買い物リスト | スコープ外 | 中核機能。**2〜5日先の献立計画**にも対応 |
| 消費量の管理 | なし | 献立確定時に減少量を計算し在庫へ反映。調理後のズレは手動修正可能 |
| 入力自動化の勝ち筋 | 「撮るだけ」（値札スキャン） | 「撮るだけ」に加え、**買い物リスト経由の購入ワンタップ確定**・レシピ確定による在庫自動引き落とし |

### なぜ変えたか

- v1系は「店頭の一瞬」だけを切り出していたが、ユーザーの実際のストレスは**冷蔵庫の把握から調理後まで連続した毎日のループ全体**にある。棚の前の比較だけ解決しても、献立を考える手間・在庫の把握・買い忘れは残る。
- 単価計算・冷蔵庫管理・レシピ・買い物リストはそれぞれ単機能アプリが存在するが、**1つのデータベースでループとしてつながった製品が空白**であり、そこに差別化を置き直した。
- v1系で確定した設計判断のうち、時間軸の考え方（買う前に効く）・入力コスト最小化・ルールベース計算・蓄積データを堀とする方針・個人利用に徹する方針は**v2.0でも維持**する。詳細は `instruction.md` §3 を参照。
