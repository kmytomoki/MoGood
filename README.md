# MoGood

**冷蔵庫の在庫 → レシピ提案 → 買い物リスト → 店頭でのお得判定 → 消費計算 → 修正**
毎日の献立サイクルを1つのデータベースで回す食材管理アプリの構想リポジトリ。

第14回 高校生ビジネスプラン・グランプリ応募中（受付 2026-08-19〜09-24）。

> **現在の段階: 未ローンチ・PoC。** アプリ本体はまだ存在しません。このリポジトリにあるのは
> 設計判断の記録・事業計画・技術検証コードです。**収支や価格の数値はすべて仮置きであり、
> 未検証です。** 検証で分かったことは、都合の悪い結果も含めてそのまま残しています。

## 解決したい課題

毎日繰り返される、この一連の手順のストレス。

1. 冷蔵庫の中をざっと把握して
2. 大体のメニューを考えて
3. 買い物へ。でもどのスーパーが安いのか、相場が分からない
4. 店頭で、なるべく安く足りない食材を頑張って選ぶ

## 何が新しいのか

冷蔵庫管理・レシピ提案・買い物リスト・単価計算は、**それぞれ単機能のアプリなら既に存在します**。
このプロジェクトの主張は、それらが1つの在庫DBを介して**毎日のサイクルとして一気通貫でつながる**ことにあります。

- 在庫が分かるから、レシピを在庫消化型で提案できる
- レシピが決まるから、不足分だけの買い物リストが自動で作れる
- リストがあるから、購入した瞬間にワンタップで在庫へ反映できる
- 献立を確定するから、消費量を先回りで計算でき、在庫の精度が保たれる

調査した範囲では、在庫→レシピ→買い物リストまでをつなぐ製品は国内外に既に存在します
（パナソニック KitchenPocket、Samsung Food、Cooklist など）。ただしそのいずれも
**「店頭で買う前のお得判定」と「調理による消費量の自動引き落とし」を同じ在庫DBに載せていません。**
差別化はこの2ステップに置いています。→ [類似プロダクト調査](20260819/類似プロダクトと収益モデル案.md)

## 設計上の中心的な賭け

**入力コストの最小化が生命線です。** 在庫管理アプリ・家計簿アプリが挫折される最大の理由は
手入力の面倒さであり、在庫DBの鮮度が落ちた瞬間にループ全体が死にます。

| 入力が発生する場面 | 自動化の手段 |
|---|---|
| 購入した食材の登録 | 買い物リスト経由のワンタップ購入確定 ＋ スキャン |
| 賞味期限 | カテゴリ別の自動推定（傷みやすい物のみ任意で上書き） |
| 調理による在庫の減少 | 献立確定時にレシピの分量から自動計算 |
| 実際の消費量とのズレ | 事後に管理画面から簡単修正（ズレを許容する設計） |

### スキャン精度の実測結果（正直に）

ローカルPC上の小型VLM（moondream）に、自作した値札風の疑似画像10枚を読ませた結果:

| 指標 | 結果 |
|---|---|
| 完全一致 | **0.0%** |
| 価格の正解率 | 20.0% |
| 商品名の正解率 | 0.0% |
| 内容量（数値/単位）の正解率 | 30.0% / 30.0% |
| 平均レイテンシ | **34.9秒**（p90: 43.7秒） |

**この構成では実用に耐えません。** 店頭で35秒待たせる時点で機能の価値はゼロです。
ローカル小型モデルでは足りないことが分かったのが、この検証の成果です。
次は API 経由の大型VLM（Gemini Flash 級）で精度・レイテンシ・1回あたり原価を実測します。

→ 詳細: [poc/ollama_shelf_scan/](poc/ollama_shelf_scan/) / [結果](poc/ollama_shelf_scan/results/results.md)

## 技術方針（要点）

- **基盤モデルは自作しない。** 既存のVLM/LLM APIを使う
- **単価換算と消費量の計算はルールベースで確実に行う。** 誤りが価格に直結するため、LLMには計算させない
- **AIの役割は「読み取り」と「名寄せ」に限定する**
- 抽出した値には必ず検算・異常値チェックを挟む
- 価格データを他ユーザーと共有・公開しない（個人利用に徹する）

技術的な参入障壁がほぼ無いことは認めた上で、防御力は蓄積データ（在庫履歴・個人の買い物台帳・
好みの学習）に置いています。
