# 収益モデル案（フリーミアム以外の選択肢）

作成日: 2026-08-18 / ステータス: **案（未検証・未採用）**
出典: `docs/instruction.md`（v2.0）/ `docs/事業プラン草案.md` §1・§3・§4 / `docs/開発プラン.md` §4
関連: `.company/departments/growth/STATE.md`

> 問題提起: 「ターゲットの節約層に月480円のフリーミアムはハードルが高い」
> → 収益の取り方を、価格の上下ではなく**払う主体・払うタイミング・原価構造**の観点から洗い直した。

---

## 0. 結論（先に3点）

1. **「節約層だから払わない」は半分誤診である。**
   `docs/事業プラン草案.md` §1.1 によれば、一次ペルソナの最大の痛みは節約ではなく「毎日『今日何作ろう』を考えるのが一番疲れる」であり、支払意欲も「月500円未満なら納得できる」と書かれている（＝480円はギリギリ内側）。
   払われない理由は価格の高さではなく、**払う時点でまだ価値が証明されていない**ことにある。

2. **本当の問題はフリーミアムの原価構造である。**
   §4.1 の仮置きでは無料1人あたり **▲27円/月**、課金転換率4%だと25人あたり **▲310円/月**。
   つまり「無料ユーザーが増えると赤字が拡大する」設計であり、**価格を下げても悪化するだけ**。
   収益アイデアは必ず「無料ユーザーの原価をほぼ0にする」案（系統D）とセットで考える。

3. **狙うべきは「安いプランを作る」ことではなく、払う主体・タイミング・形式をずらすこと。**
   以下、系統A〜Dに整理した。

---

## 1. 系統A: 払う「タイミング」をずらす（節約層に最も効く）

| # | 案 | 中身 | 評価（正直に） |
|---|---|---|---|
| A-1 | 節約額の後払い型 | 「今月2,400円得しました → うち480円」。浮いた金から払う建て付け | 心理的には最強だが、**ストア課金は成果報酬に非対応**で実装困難。現実版は A-2 |
| A-2 | **節約保証（実質後払い）** | 「今月の節約額が料金を下回ったら翌月無料」。節約額は買い物台帳から算出 | ストア課金のままクーポン運用で実現可能。**有力候補**。ただし節約額の算出根拠が弱いとクレーム源になる |
| A-3 | **課金の起点をゲートにする** | 無料期間を日数ではなく「**在庫が2週間続いたら課金開始**」に紐づける | 価値証明の後に課金が来る。しかも物差しが Phase 0-① の検証指標と同一で一貫性がある。**有力候補** |
| A-4 | クレジット（回数）プリペイド | 「スキャン100回パック 300円」など | **原価と収益が構造的に連動する唯一の案**（使われるほど赤字にならない）。サブスク嫌いの層に刺さる。ARPU は低い |
| A-5 | **世帯課金** | 1契約で夫婦・祖父母が同じ在庫DBを共有 | 献立は世帯の課題。CAC そのままで ARPU 上昇。在庫DBが1つという設計と自然に噛み合う。**低コストで効く** |

## 2. 系統B: ユーザー以外が払う（B2B2C）

| # | 案 | 中身 | 評価（正直に） |
|---|---|---|---|
| B-1 | **リワード広告を原価に直結** | 「動画1本見ればスキャン1回」。API原価が発生する行動にだけ広告を当てる | 節約層は**金ではなく時間で払う**層。▲27円/月の穴埋めとして現実的。**有力候補** |
| B-2 | 食品メーカーの文脈型タイアップ | 在庫に豆腐があるとき、メーカー提供の使い切りレシピを提案理由つきで出す | 端末側マッチングなら個人データを外に出さずに実装可（確定事項8と両立）。ただし**「提案が中立である」という信頼を削る**のが最大のリスク |
| B-3 | ネットスーパー・生協の注文連携 | 買い物リストをそのままカートへ送る成果報酬 | 共働き世帯とは相性が良い。ただし「安く買う」訴求とは逆行しうる |
| B-4 | **自治体のフードロス削減予算** | 住民向けの実証事業・共同研究として委託を受ける | 自治体は食品ロス削減計画と予算を実際に持つ。**現段階のチームが最初に現金を得る現実的な経路**。要調査 |
| B-5 | 食育・家庭科の教材ライセンス | 「食材を使い切る」学習教材として学校へ提供 | 高校生チームという立場が強みになる希少な市場。単価は小さいが実績になる |
| B-6 | 企業の福利厚生バンドル | 共働き支援として法人経由で配布 | 中期。営業力が必要で現段階では非現実的 |

## 3. 系統C: 価値訴求の付け替え（価格を変えずに払われるようにする）

- **C-1 売り物を「節約」から「時間」へ**
  「月2,000円の節約」は疑われるが「毎日15分の『何作ろう』が消える」は疑われにくく、**検証で否定されにくい**。節約額は副次的な証拠として添える。
- **C-2 表示単位を変える**
  「480円/月」ではなく「**1日16円 / 今月の節約2,400円**」。同じ金額でも支出ではなく回収の話に見える。
- **C-3 ポイント経済との接続**
  節約層は現金より「ポイントで払う」抵抗が低い。ポイ活層との提携・付与は認知施策としても効く。
- **C-4 課金境界の見直し（重要）**
  現案（§3.1）は「2〜5日先の献立計画」を課金側に置いているが、**計画こそがループの入口＝最大の価値**であり、価値証明の前に壁が来てしまう。
  有料側は「買い物台帳・節約レポート・好み学習」（＝蓄積して効く＝解約しにくい）へ寄せる方が、堀の考え方（`docs/instruction.md` §2.4）とも一貫する。

## 4. 系統D: 原価側（収益案と同じだけ損益に効く。A〜Bどれを選んでも必須）

- 定番レシピ・定番商品は**事前バッチ生成＋キャッシュ**で API 呼び出しを共有する（同じ在庫パターンへの提案は再利用可能）
- 無料ユーザーの提案は「その日の共通献立候補」から選ぶ形にすれば、1日1回の生成を多人数で割れる
- 単価換算・消費量計算はルールベースで原価0（既に確定事項7・§4.1）

## 5. 却下する案（`instruction.md` の確定事項に抵触）

| 案 | 抵触先 |
|---|---|
| 匿名集計した価格データの小売・メーカーへの販売 | 確定事項8（価格データを共有・公開しない） |
| ユーザー投稿型の価格DBを構築して提供 | 確定事項8 ＋ 事業プラン §3.1（小売連携・価格データ提供は採らない） |

これらを採用する場合は**確定事項の変更**であり、CEO 判断と `docs/バージョン履歴.md` のバージョン更新が必要。勝手に前提を崩さないこと。

## 7. 次の一手

収益モデルの変更は仮説検証ゲートの対象（新収益源・新チャネル）。順序は以下。

1. **Phase 0 の API 原価実測を入れて §4.1〜4.2 を引き直す** → B-1 または A-4 で無料ユーザーの原価を賄えるかを机上で確認する
2. **ヒアリングで価格ではなく「払う形式」を聞く**（サブスク／回数券／広告を我慢／節約保証のどれなら使うか）。`docs/ヒアリング手順_友人家族.md` 本題D に1問足すだけで足りる
3. 通った案のみ `docs/事業プラン草案.md` §3.1・§4 に反映（既存 docs の書き換えなので差分を提示して承認を得る）

**未検証の数値を断定形で書かないこと。** 本ファイルの数値はすべて §4.1 の仮置き前提に基づく。
