# MoGood アプリ開発プラン

作成日: 2026-07-17 / 更新日: 2026-07-18（課題再定義 v2.0 対応） / ステータス: **提案（技術スタックは `instruction.md` §9 で未確定。本プランの採否が決まったら §9 を更新すること）**

---

## 0. 結論（先に要点）

- **フロントエンド**: React Native + Expo（iOS/Android同時、ベータ期のOTA更新が武器）
- **バックエンド**: Python + FastAPI を Cloud Run に載せる（PoCの `unit_price.py` / `schema.py` をそのまま流用できる）
- **DB/認証/ストレージ**: Supabase（PostgreSQL）。**在庫・レシピ・買い物リスト・購入履歴を1つのDBでつなぐ**ことが最重要要件。第2弾以降のドメイン追加にも耐えるスキーマ設計にする
- **VLM/LLM**: Gemini Flash 系を主軸、Claude をフォールバック/精度比較用に併用。レシピ提案は**キャッシュ前提**で設計（原価の主戦場）
- **UI参考**: 在庫は「pecco + マネーフォワード ME」、レシピは「クラシル」、買い物リストは「Bring! / Google Keep」、スキャン体験は「Vivino + Googleレンズ」
- **順序**: Phase 0 検証（**在庫が2週間続くかの紙プロト** + スキャンのレイテンシ・精度・原価の実測）を最初に置く。**ここを通過するまでアプリ本体は作らない**

## 1. UIの参考にすべき既存アプリ（画面・体験ごと）

自分より先に同じ問題を解いたアプリの「型」を借りる。ゼロから発明しない。

### 1.1 在庫・期限管理（ループの土台）

| 参考アプリ | 借りるべき型 | 理由 |
|---|---|---|
| **pecco** など冷蔵庫管理系 | 在庫リスト → レシピ提案の導線。期限が近いものを上に出すソート | 在庫→提案の基本導線の完成形。ただし手入力前提の登録導線は真似しない |
| **マネーフォワード ME** | 「自動で貯まる台帳」の見せ方。月次レポート・推移の画面 | 在庫・消費履歴が資産に見えるUI。家計簿アプリの挫折原因（手入力）を自動化で回避した点も設計思想ごと参考にする |
| **あすけん** | 毎日の小さな記録が長期グラフに積み上がる達成感の演出 | 継続率を作る画面設計 |

**設計指針**: 在庫一覧は「期限が近い順」がデフォルト。修正（数量の増減）は一覧から2タップ以内で完了させる（`instruction.md` 確定事項4「ズレ許容+簡単修正」）。

### 1.2 レシピ提案（毎日の入口）

| 参考アプリ | 借りるべき型 |
|---|---|
| **クラシル / デリッシュキッチン** | サムネイル一覧のレシピUI。ペルソナ（事業プラン§1.1）が既に使い慣れている型 |
| **Netflix等のレコメンド行** | 「在庫を使い切る」「あなたの好み」など**提案の理由ごとに行を分ける**カルーセル。在庫縛り案と好み寄り案を並べて出す（確定事項3）はこの型で実現する |

**設計指針**: 提案理由（「賞味期限が近い鶏ももを使います」）をカードに明示する。理由が見えると提案への信頼が立ち上がる。

### 1.3 買い物リスト（自宅と店をつなぐ）

| 参考アプリ | 借りるべき型 |
|---|---|
| **Bring! / Google Keep（リスト）** | チェックで消える買い物リストの操作感。片手・店内・数秒で操作できる大きなタップ領域 |
| **Todoist** | 「今日/明日/週末」のような日付グルーピング。2〜5日先の献立計画からのリスト分割に流用 |

**設計指針**: リストの品をチェックした瞬間に**在庫へのワンタップ購入確定**を兼ねさせる（確定事項2）。「リスト消化=在庫登録」で入力コストをゼロに近づける。ここが本アプリの入力自動化の本丸。

### 1.4 店頭スキャン（お得判定）

| 参考アプリ | 借りるべき型 | 理由 |
|---|---|---|
| **Vivino**（ワインラベルスキャン） | 「撮影 → 解析中アニメーション → 結果カード」の3ステップフロー | 「撮るだけで商品情報が返る」体験の完成形 |
| **Googleレンズ / Google翻訳カメラ** | 検出した対象に枠をオーバーレイ表示し、タップで詳細 | 複数商品が写る場合、「どれを読み取ったか」の可視化が信頼感に直結する |
| **価格.com** | 単価順ソート + 最安バッジ。「何を基準に並んでいるか」（100gあたり等）を常時表示 | 判定結果の見せ方 |
| **安値帳** | 底値との比較表示（「いつもよりお得/割高」） | 個人台帳との比較表示（確定事項5）。ただし手入力前提の導線は真似しない |

**設計指針**: シャッター → 結果まで無操作。結果画面の主役は「お得バッジ + 差額 + いつもとの比較」。数字の羅列にしない。

### 1.5 献立確定・消費計算

| 参考アプリ | 借りるべき型 |
|---|---|
| **ECの注文確認画面** | 「この献立を確定すると在庫がこう減ります」の差分プレビュー → 確定ボタン。減少量を確定前に見せて安心させる |
| **あすけん（食事記録の事後修正）** | 「実際はもっと使った/残した」の事後スライダー修正。完璧を求めない記録UI |

## 2. フロントエンド

### 推奨: React Native + Expo

| 観点 | 評価 |
|---|---|
| クロスプラットフォーム | iOS/Android 同時リリース。個人〜少人数開発で二重実装は不可能 |
| カメラ | `react-native-vision-camera` で撮影・圧縮まで完結。VLM解析はサーバー側なので端末性能への依存が小さい |
| イテレーション速度 | Expo EAS の OTA 更新でベータ期の修正をストア審査なしに配布できる。**検証〜ベータの高速な仮説検証と相性が良い** |
| 採用・情報量 | TypeScript 圏のエコシステムが使える |

**正直なトレードオフ**: Flutter でも成立する（カメラ・描画の安定性はむしろ Flutter が上との評価もある）。決定打は「ベータ期のOTA更新」と「バックエンドとフロントで言語を分ける前提なら、フロントは情報量の多いTS圏が無難」の2点。開発者がDart経験者ならFlutterに変えてよい。**ネイティブ2本体制だけは選ばない**こと。

### 画面構成（MVP）

1. **ホーム**: 今日のレシピ提案（在庫消化行 + 好み行）+ 期限が近い在庫アラート（1.1 / 1.2の型）
2. **在庫**: 一覧（期限順）・検索・2タップ修正（1.1の型）
3. **買い物リスト**: 日付グルーピング + チェック=購入確定（1.3の型）
4. **スキャン**: カメラ → お得判定（1.4の型）
5. **献立確定**: 消費量の差分プレビュー → 確定 →（調理後）事後修正（1.5の型）
6. **台帳・レポート**: 値動き履歴・「今月の節約額」（Phase 4、課金側）

## 3. バックエンド

### 推奨: Python + FastAPI on Cloud Run、Supabase（PostgreSQL / Auth / Storage）

| 構成要素 | 選定 | 理由 |
|---|---|---|
| API サーバー | **FastAPI**（Python） | PoC の `unit_price.py`・`schema.py`（Pydantic）を**そのまま本番コードに昇格できる**。VLM/LLM SDK も Python が最充実 |
| 実行基盤 | **Cloud Run** | 利用は朝夕にバーストする（献立時間・買い物時間）。ゼロスケールで固定費最小、事業プラン§4.1の「固定費 月3万円」に収まる |
| DB / 認証 | **Supabase**（PostgreSQL） | RDB であることが必須（在庫×レシピ×リスト×履歴の JOIN がアプリの本体。将来の家計・日用品ドメインとも JOIN）。Firestore 等の NoSQL は不採用。Auth・Row Level Security 込みで個人データ保護（確定事項8）と相性が良い |
| 画像ストレージ | Supabase Storage | 解析後は**原則即削除**（§5 プライバシー参照）。恒久保存しないので容量コストは小さい |
| VLM（スキャン） | **Gemini Flash 系**を主軸 | 1スキャン原価 ≤1〜2円（事業プラン§4.3の成立条件）を満たせる可能性が最も高い。Claude は精度比較・フォールバック用 |
| LLM（レシピ提案・名寄せ） | 同上の軽量モデル + **キャッシュ層** | 提案は毎日呼ばれるため原価の主戦場。同一在庫パターン・定番提案の再利用で実効原価を圧縮する |

### 主要パイプライン

**A. レシピ提案（1日1〜2回）**

```
FastAPI:
  1. 在庫（数量・期限）+ 好み設定 + 直近の献立履歴を取得
  2. キャッシュ確認（同等の在庫パターンへの提案があれば再利用）
  3. LLM に文脈を渡し、「在庫消化案」「好み寄り案」を構造化JSONで生成
  4. Pydantic で検証（存在しない在庫を使っていないか等）
  5. 提案カードとして返却・キャッシュ保存
```

**B. 献立確定 → 消費計算（ルールベース、LLM不使用）**

```
  1. レシピの分量 × 人数 → 必要量を算出
  2. レシピ食材と在庫アイテムの名寄せ（事前にマッピング済み。未知のものだけLLMで補助）
  3. 在庫から減算（調味料は標準換算辞書: 大さじ1=15ml等）
  4. 差分プレビューを返し、確定で書き込み。事後修正は上書きで対応
```

**C. 店頭スキャン（1スキャン）**

```
クライアント: 撮影 → 端末内で長辺1280px程度に圧縮（~200KB）
    ↓ POST /scan
FastAPI:
  1. VLM に画像を投げ、構造化JSON（商品名・価格・容量・単位）を取得
  2. Pydantic で検証 + 異常値チェック（価格0円、単価が相場の10倍等は弾く）… instruction.md §4.1「必ず検算」
  3. unit_price.py（ルールベース）で共通単価に換算 … LLMに計算させない（禁止事項）
  4. 同種商品のグルーピング（ここはLLMに任せる）+ 個人台帳との比較（いつもより安い/高い）
  5. 単価順に整列して返却。購入したらワンタップで在庫・台帳へ記録
```

**レイテンシ予算（スキャン合計 5秒以内を目標、Phase 0で実測)**: 圧縮0.5s / アップロード0.5s / VLM 2〜3s / 検証・換算・整列 0.5s / 描画 0.5s

### DBスキーマ骨子（第2弾以降への流用を意識）

```
users                 -- Supabase Auth 連携
pantry_items          -- 在庫（数量・単位・賞味期限）★ループの土台
expiry_defaults       -- カテゴリ別標準日数の辞書（instruction.md 確定事項6）
recipes               -- レシピ（提案生成分 + 定番）。食材と分量を構造化して持つ
ingredient_map        -- レシピ食材名 ↔ 在庫アイテムの名寄せ辞書
meal_plans            -- 献立計画（日付・レシピ・人数・確定/調理済みステータス）
consumptions          -- 消費記録（自動計算分 + 事後修正の差分）
shopping_list_items   -- 買い物リスト（由来レシピへの参照・予定日・購入確定フラグ）
purchases             -- 購入記録 = 個人の買い物台帳（価格履歴の堀）
scans / scan_items    -- スキャンイベントと読み取り結果
preferences           -- 明示設定 + 選択履歴から推定した好み
domains / item_kinds  -- 「食品」を1ドメインとして抽象化。日用品・家計を後から追加できる親テーブル
```

ポイント: `pantry_items` の鮮度がすべての機能の前提。**「リストのチェック=purchases+pantry_items への書き込み」「献立確定=consumptions+pantry_items の更新」という、操作のついでに自然にDBが更新される導線**を最優先でUXに組み込む。

## 4. 開発フェーズ

| フェーズ | 内容 | 完了条件（ゲート） |
|---|---|---|
| **Phase 0: 検証**（最優先） | ① **在庫継続性**: 紙 or スプレッドシートで「リスト経由の購入確定+レシピ分の引き落とし+事後修正」を2週間自己運用し、在庫の鮮度が保てるか検証 ② **スキャン実測**: 実店舗の値札・ラベル10〜20枚をクラウドVLM（Gemini/Claude）で レイテンシ・精度・1スキャン原価 を実測（既存PoC `poc/ollama_shelf_scan` を実写+クラウドAPI対応に拡張） ③ レシピ→消費量換算のズレを数件の実調理で確認 | ①在庫が2週間実態と大きく乖離しない ②撮影→提示 ≤5s、価格抽出精度 ≥90%、原価 ≤2円/スキャン ③修正が苦にならない。**未達なら方式再検討、アプリ開発に進まない** |
| **Phase 1: 在庫コア** | 画面2（在庫）+ 初回セットアップ一括登録 + カテゴリ別期限推定 + 2タップ修正 + 匿名認証。MVP機能1・6 | 自分の冷蔵庫を2週間アプリで管理し、実態との乖離が許容内 |
| **Phase 2: ループ完成** | 画面1・3・5（レシピ提案/買い物リスト/献立確定・消費計算）。MVP機能2・3・5。提案キャッシュ層もここで入れる | 「提案→リスト→購入確定→確定→引き落とし→修正」が一周する。自分で1週間、毎日回して破綻しない |
| **Phase 3: 店頭スキャン** | 画面4（スキャン→お得判定→ワンタップ在庫登録）。MVP機能4 | 3店舗・2週間の自己検証で、店内で使い物になる |
| **Phase 4: 計画と台帳** | 2〜5日先の献立計画 + 台帳・「今月の節約額」+ 好みの学習（課金側機能） | ベータ配布（TestFlight / Google Play内部テスト、10〜30人）開始。継続率・課金意向の計測（事業プラン§4.3） |
| **Phase 5: 公開準備** | ストア審査対応・利用規約/プライバシーポリシー・課金実装（RevenueCat推奨） | ストア公開 |

各フェーズは前のゲートを通ってから着手する。特に **Phase 0 を飛ばして Phase 1 に進まない**（instruction.md 禁止事項）。

## 5. 非機能・横断事項

- **プライバシー**: 撮影画像は解析後に即削除をデフォルトにする。店舗内撮影への配慮（確定事項8「共有しない個人利用」）を利用規約にも明記
- **コスト制御**: ユーザーごとのスキャン回数・提案生成回数を最初からメータリングする（無料枠の実装 + 原価モニタリング）。API課金の暴走が事業リスク（事業プラン§4.1）。レシピ提案はキャッシュヒット率も計測する
- **オフライン耐性**: 店内は電波が弱いことがある。買い物リストのチェックは**オフラインでも動作**させ、後で同期。スキャンはアップロード失敗時のリトライキューと圧縮済み画像のローカル保持を初期から入れる
- **計測**: Phase 1 から「在庫の更新頻度・修正頻度・スキャン成功率・所要秒数・原価」をイベントログとして収集。Phase 0 の実測を本番でも継続する構え
