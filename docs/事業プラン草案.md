## 0. サマリー（結論を先に）

- **誰に**: 「毎日の『冷蔵庫を把握→献立を考える→買い物で選ぶ』の繰り返しに疲れている」共働き・子育て世帯の食事管理者（一次ペルソナ: 34歳・時短勤務・週3回スーパー）
- **なぜ選ばれる**: 冷蔵庫管理・レシピ・買い物リスト・単価計算はそれぞれ単機能アプリが存在するが、**1つの在庫DBで毎日のループとしてつながった製品はほぼ空白**。さらに使うほど在庫履歴・買い物台帳・好み学習が貯まり、乗り換えにくくなる
- **どう届ける**: フリーミアム（無料=在庫管理+当日のレシピ提案、プレミアム=月480円で数日先の献立計画・スキャン無制限・台帳）。App Store / Google Play 直販。認知は節約・時短系SNSとASO
- **成り立つか**: 粗利構造は成立しうるが、**APIコスト（スキャン+レシピ生成）が最大の変動費**。無料枠の設計と1回あたり原価（§6検証項目）が損益の生命線

## 1. 顧客（Target Customer）

### 1.1 一次ペルソナ: 「献立疲れの共働きママ」佐藤 美咲（仮名）

| 項目    | 内容 |
| ----- | --------------------------------------------------------------------- |
| 基本属性  | 34歳女性・川崎市在住・時短勤務（事務職）・夫と子供2人（5歳・2歳） |
| 世帯    | 世帯年収650万円。食費は月約7万円で、物価高騰により2年前から+1万円増 |
| 買い物行動 | 週3回、駅前スーパーと格安スーパーを使い分け。買い物前に冷蔵庫を覗いて頭の中で献立を組み、店では**急いで安い方を選ぶが、確信はない**。買い忘れ・二重買いもしばしば |
| デジタル  | iPhone利用。LINE・Instagram中心。レシピはクックパッド/クラシル。家計簿アプリは3回挫折（**手入力が続かない**） |
| 痛み    | 「毎日『今日何作ろう』を考えるのが一番疲れる」「冷蔵庫に何があるか出先で思い出せない」「特売品を買ったのに腐らせて自己嫌悪」「棚の前でどれが得か即断できない」 |
| 求める状態 | **考えずに・回る**。献立と買い物が半自動で回り、手間ゼロで月数千円浮けば十分満足 |
| 支払意欲  | 月500円未満なら「浮いた分で元が取れる」と納得できるライン（要検証） |

**選定理由**: 「把握→献立→買い物→調理」のループを毎日回している当事者であり、来店・調理頻度が高いため蓄積データ（在庫履歴・台帳・好み）の価値が最も早く立ち上がる層。家計簿アプリ挫折経験は「入力させない設計」（`instruction.md` §2.2）の必要性の裏付けでもある。

### 1.2 二次ペルソナ: 「自炊を始めた一人暮らし」田中 蓮（仮名）

- 28歳男性・都内一人暮らし・年収450万円。物価高で自炊を開始したが、相場観がなく「これは高いのか安いのか」が分からない。買った食材の使い切りに失敗しがちでフードロス罪悪感がある。献立のレパートリーが少なく、同じものばかり作ってしまう。
- MoGoodには「相場を知る先生」「在庫からのレシピ提案」「期限リマインド」を期待する。一次ペルソナより課金率は低い想定だが、口コミ（SNS）発信力が高い。

### 1.3 ターゲットにしない層（明示しておく）

- 底値ノートを自作するような**節約ガチ勢**: 手入力アプリで満足しており、精度要求が厳しくクレーム源になりやすい
- 食費・献立に無関心な層（外食中心・高所得）: 痛みがなく定着しない
- 完璧な在庫記録を求める几帳面層: 本アプリは「ズレ許容+簡単修正」設計であり、グラム単位の正確性は保証しない

## 2. 競合優位性（Competitive Advantage）

### 2.1 競合マップ

| 競合                    | できること      | できないこと（MoGoodとの差） |
| --------------------- | ---------- | ---------------------------- |
| 冷蔵庫・在庫管理アプリ（pecco等） | 在庫・期限の管理、簡単なレシピ提案 | **入力が手動中心で続かない**。買い物リスト・店頭のお得判定と連動しない |
| レシピアプリ（クックパッド・クラシル） | レシピ検索・献立のアイデア | 自宅の在庫を知らないため「あるもので作る」提案ができない。買い物リストが在庫と連動しない |
| 買い物リストアプリ | リストの作成・共有 | レシピ・在庫と切れており、リスト作成自体が手作業 |
| 単価計算アプリ・Webツール（多数、無料） | 単価の計算 | **すべて手入力**。店内で急いでいると使われない |
| トクバイ・Shufoo!（チラシアプリ）  | 特売情報の事前入手  | チラシ掲載品のみ。棚の前での商品間比較・在庫連動なし |
| Googleレンズ等の汎用画像検索     | 商品の識別      | 単価換算・在庫への反映・個人の履歴蓄積がない |

**空白地帯**: どの競合も上記の1機能に特化しており、「在庫 → レシピ → 買い物リスト → 店頭判定 → 消費反映」を1つのDBでつなぐ製品はほぼ存在しない。

### 2.2 選ばれる理由（3層で言語化）

1. **機能の差: ループがつながっている**
  在庫が分かるからレシピが在庫消化型になり、レシピが決まるから不足分だけの買い物リストが自動で作れ、リストがあるから購入のワンタップ確定で在庫が更新される。**個々の機能は模倣可能だが、体験としての「回る感」は統合でしか作れない。**
2. **体験の差: 入力させない + 縛らない**
  家計簿・在庫アプリの挫折原因である手入力を、リスト経由のワンタップ確定・スキャン・消費の自動計算で排除。レシピ提案も「在庫のみ」に縛らず好み寄りの案を併記し、窮屈さを避ける。
3. **堀（持続的優位）: 蓄積データ**
  技術自体は汎用AIで模倣可能であり、技術的参入障壁はない（正直に認める）。防御力は (a) 在庫・消費の履歴（我が家の回し方データ）、(b) 個人の買い物台帳（値動き履歴）、(c) 選択履歴からの好み学習に置く。**使うほど馴染む=乗り換えコスト**が本当の優位性。

### 2.3 優位性が崩れるシナリオ（リスクの言語化）

- クックパッド・クラシル級の大手が在庫管理と買い物リストを統合した場合、機能差は薄まる → 蓄積データの先行でしか守れない。**ローンチ後は在庫DBの継続利用率（鮮度維持率）をKPIの中心に置く**
- 在庫入力・修正が面倒で続かなければ価値はゼロ（§6検証が未了のうちは、本プランの前提すべてが仮）

## 3. マーケティング・販売戦略（Business Model）

### 3.1 価格とプラン（フリーミアム）

| プラン   | 価格                   | 内容 |
| ----- | -------------------- | --------------------------------------------- |
| 無料    | ¥0                   | 在庫管理（数量・期限）・**当日分**のレシピ提案・買い物リスト・店頭スキャン**月20回**（初回からループを一周体験させる） |
| プレミアム | **月480円**（年払い¥4,800） | **2〜5日先の献立計画**・スキャン無制限・買い物台帳（値動き履歴）・好み学習・「今月の節約額」レポート |

- 設計意図: 無料版で「ループが回る」体験までを開放し、有料版は「先まで計画できる」「蓄積して効く」価値を開放する。堀となる蓄積機能を課金側に置くことで、課金＝定着になる。
- 480円の根拠（仮説）: 献立時間の短縮 + 月2,000〜3,000円の節約実感が出れば元が取れる計算が成立する価格。ただし**支払意欲は未検証**。ベータ版で価格受容性テスト（PSM調査）を行う。
- 収益モデルの選択肢のうち**小売連携・価格データ提供は現時点で採らない**（`instruction.md` 確定事項8「個人利用に徹する・価格データ非共有」に抵触するため）。サブスク一本で検証する。

### 3.2 チャネル

- **販売**: App Store / Google Play 直販のみ（EC・実店舗なし。手数料15%を原価に織り込む ※小規模事業者プログラム適用前提）
- **利用場面**: 自宅（献立・在庫）と店内（スキャン・リスト消化）の2場面。店内はオフラインに近い環境でも動くようレイテンシ・リトライ設計がマーケ上も生命線

### 3.3 認知獲得（ペルソナの生息地に絞る）

| フェーズ       | 施策 | 狙い |
| ---------- | --------------------------------------------------------------------------- | ------------------- |
| ベータ（〜100人） | 知人・地域の子育てコミュニティ・X/Instagramの節約/時短アカウントに直接声かけ | §6検証と価格受容性テストを兼ねる |
| ローンチ期      | 節約・時短系インスタグラマー/TikTokerへのギフティング（「冷蔵庫を撮ると今晩の献立が決まる」「撮るだけでどれが得か分かる」は動画映えする）、ASO（「献立 アプリ」「冷蔵庫 管理」「買い物リスト」「単価 計算」） | CAC低めの獲得。動画1本での体験理解 |
| 成長期        | 「今月いくら得したか」「今月使い切った食材」レポートのSNSシェア機能、メディア掲載（物価高騰・フードロスは追い風の時事テーマ） | 口コミの仕組み化 |

- 仮置きCAC: 500円/インストール以下を目標（有料広告は当面使わず、オーガニック中心）
- 初期離脱対策: 在庫が空だと提案の質が低い既知リスクに対し、**初回セットアップの一括登録 → その場で「今晩の3案」提案**までを最初の5分で体験させる設計とする

## 4. 収支計画（Financial Plan）

> **前提がすべて仮置き**である点に注意。特に「1回あたりAPI原価」（スキャン・レシピ生成）は§6の実測で必ず差し替えること。

### 4.1 前提（単位経済）

| 項目            | 仮置き値     | 根拠・メモ |
| ------------- | -------- | ---------------------------------- |
| プレミアム価格       | 月480円    | §3.1 |
| ストア手数料        | 15%      | 小規模事業者プログラム |
| 1スキャンAPI原価    | **1.0円** | 軽量VLM（Gemini Flash級）想定。**§6で実測必須** |
| 1レシピ提案API原価  | **0.5円** | 軽量LLM+キャッシュ前提。**§6で実測必須** |
| 無料ユーザーの月間API利用 | スキャン12回+提案30回 | 週3回来店×1スキャン、提案は1日1回想定 |
| 有料ユーザーの月間API利用 | スキャン40回+提案60回 | 週3回来店×3スキャン、提案は1日2回想定 |
| 課金転換率（MAU比）   | 4%       | フリーミアム一般値3〜5%の中央 |
| サーバー等固定費      | 月3万円     | MVP規模（サーバレス構成想定） |

**ユーザー1人あたり月次の粗利（ユニットエコノミクス）**

- 有料1人: 収入 480×0.85 = 408円 − API原価 (40+30)=70円 = **粗利 338円/月**
- 無料1人: 収入 0円 − API原価 (12+15)=27円 = **▲27円/月**
- → 有料1人が無料ユーザー約12人分の原価を賄える。**課金率4%（無料24人:有料1人）では▲310円/25人でわずかに赤字となり、v1系より構造が厳しい**。レシピ提案のキャッシュ率を上げて無料の提案原価を1/3に圧縮するか、課金率5%以上が必要。→ **提案のキャッシュ設計とAPI原価が損益の生命線**

### 4.2 3ヵ年シミュレーション（月次ベース、年度末時点）

| 指標              | 1年目          | 2年目          | 3年目          |
| --------------- | ------------ | ------------ | ------------ |
| MAU             | 1,000        | 5,000        | 20,000       |
| 課金ユーザー（転換率）     | 30（3%）       | 200（4%）      | 1,000（5%）    |
| 月間売上（手数料控除後）    | 12,240円      | 81,600円      | 408,000円     |
| API原価（無料+有料）    | ▲28,290円     | ▲143,600円    | ▲583,000円    |
| 固定費（サーバー等）      | ▲30,000円     | ▲30,000円     | ▲50,000円     |
| **月次損益（人件費除く）** | **▲46,050円** | **▲92,000円** | **▲225,000円** |

- 読み方: **上記の仮置き原価のままでは3年目でも赤字**であり、v1系（スキャン単機能）より原価構造が重い。成立させるには ① レシピ提案のキャッシュ・作り置きで提案原価を1/5〜1/10に圧縮（同じ在庫パターンへの提案は再利用可能なので現実的）、② 課金率5%以上、③ 無料の提案回数制限、のいずれか複数が必要。
- 感度が大きい変数（優先順に）: ① レシピ提案の実効API原価（キャッシュ率） ② 1スキャン原価 ③ 課金転換率。§6の実測後にこの表を必ず引き直すこと。

### 4.3 成立条件のまとめ（検証すべき仮説）

1. **実効API原価 ≤ 1〜2円/日/ユーザー**（キャッシュ込みの実測。超えるなら無料枠を絞る等の再設計）
2. **在庫DBの2週間継続率**（`instruction.md` §6-1。ここが崩れると課金価値そのものが消える）
3. **課金転換率 ≥ 4〜5%**（献立計画・台帳に課金価値を感じるかのベータ検証）
4. **月次解約率 ≤ 5%**（LTV = 338円粗利 ÷ 5% ≒ 6,760円 → CAC 500円に対し十分。解約率10%でも成立するが余裕が薄い）
