## 0. 班の役割分担（迷ったらここを見る）

| 班 | 担当すること | 担当しないこと |
|---|---|---|
| **AI班** | ラベル・値札の読み取り（精度・速度・APIコスト）、レシピ提案のプロンプト、単価換算・**消費量換算**のルール本体、賞味期限カテゴリ辞書、レシピ食材と在庫の名寄せ、アプリに渡すJSONの形 | 画面の見た目・画面遷移・ストア申請・「きれいなUI」 |
| **アプリ班** | スマホ画面・在庫/リスト/スキャンの導線・結果の見せ方・ユーザー体験 | モデルの学習・プロンプトの本丸・単価/消費量計算ロジックの発明 |

**重要な約束**: アプリ本体の本格つなぎ込みより先に、**Phase 0 検証（在庫継続性・スキャンのレイテンシ/精度/原価・消費量換算の妥当性）**をやる。未達のままレコメンドの高度化に進まない（`instruction.md` 禁止事項）。

**AI班が最初に届ける成果物**: 「この写真を渡すと、このJSONがこの秒数・この円で返る」という**数値つきの実験レポート**。かっこいいデモより数字。

## 1. 今週〜すぐやること（コードを書かなくても進む）

経験ゼロでも着手できる。チェックが全部ついたら「準備完了」。

### A. プロダクトと「AIの役割」を自分の言葉で説明できる

- [ ] `instruction.md` の §1〜§2・§4・§6・§8 を読む
- [ ] 1分で説明できるようにする: 「在庫はDBで自動管理 → AIが在庫消化と好みのレシピを提案 → 不足分が買い物リストに → 店ではラベルを撮るだけでお得判定 → 献立確定で在庫が自動で減る → ズレたら簡単修正」
- [ ] **AIがやること／やらないこと**を覚える:
  - 読み取り（ラベル・値札）と名寄せと提案文の生成は AI
  - **単価計算・消費量計算はルール（プログラム）**。AIに計算させない
  - レシートOCRを主軸にしない／価格データを他ユーザーと共有しない
  - 基盤モデルを自作・学習しない（既存VLM/LLM APIを使う）
  - Phase 0 検証を飛ばして機能を増やさない

**完了の目安**: 「AIがやる部分」と「プログラム（ルール）がやる部分」を口頭で分けて言える。

### C. 検証用の「値札・ラベル写真セット」を集める（Phase 0 の材料）

疑似画像だけでは不十分（PoCのREADMEにも記載）。**実店舗の値札・商品ラベル**が本命。

集め方のルール（プライバシー・店舗配慮）:

- 個人利用・検証目的。他人の顔やレシート全体が写らないようにする
- 価格をSNSや公開リポジトリに載せない（確定事項: 価格データ非共有）
- 店内で長時間止まらない・店員に指摘されたらすぐやめる

集めるバリエーション（合計 **10〜20枚** が目標）:

- [ ] 印刷のきれいな値札（スーパー定番）
- [ ] 手書き・ポップ風
- [ ] 斜め・少し暗い・反射あり
- [ ] g / kg / 枚 / パック数など単位が違うもの
- [ ] **商品ラベル込み**の写真（値札+パッケージが1枚に写るもの。v2.0 の「ラベル込みスキャン」の想定入力）
- [ ] 同じ棚に複数商品が写っているもの（余裕があれば）

記録用シート（スプレッドシートでよい）:

| 写真ID | 正解:商品名 | 正解:価格(円) | 正解:容量 | 正解:単位 | メモ（手書き等） |
|---|---|---|---|---|---|
| tag_001 | | | | | |

- [ ] 10枚以上＋正解シート v1 ができた
- [ ] 共有場所を決め、アプリ班にも「こういう写真を読む」と見せた

### C2. 消費量換算の「標準辞書」の種を作る（コード不要）

献立確定→在庫引き落とし（MVP機能5）の材料。スプレッドシートでよい。

- [ ] 調味料の標準換算を20個書き出す（大さじ1=15ml、醤油大さじ1=18g など。出典もメモ）

- [ ] 食材カテゴリ別の賞味期限のたたき台を15カテゴリ書く（葉物3日、卵2週間 等）

|---|---|---|---|---|---|---|

- [ ] 10枚以上で表を埋めた
- [ ] **集計**を出す:
  - 平均レイテンシ（秒）
  - 価格が正解だった割合
  - 1スキャンあたりのざっくり原価（APIの料金表 × 入出力トークン or 公式の概算）

### J. アプリ班に渡す「契約」（APIの形）

画面側がダミーから本物に差し替えられるよう、**先に形を合意**する。

スキャン結果の最低限のレスポンス例:

```json
{
  "latency_ms": 2300,
  "items": [
    {
      "name": "豚こま切れ",
      "price_yen": 298,
      "quantity_value": 200,
      "quantity_unit": "g",
      "unit_price_yen": 149.0,
      "basis": "per_100g",
      "is_best_deal": true,
      "vs_my_usual": "cheaper"
    }
  ],
  "errors": []
}
```

レシピ提案の最低限のレスポンス例:

```json
{
  "proposals": [
    {
      "title": "鶏ももと葉物の炒め物",
      "reason": "use_up_expiring",
      "uses_from_pantry": [{"item": "鶏もも", "amount": 250, "unit": "g"}],
      "missing": [{"item": "ピーマン", "amount": 3, "unit": "個"}]
    }
  ]
}
```

- [ ] フィールド名をアプリ班と文書で合意した
- [ ] `unit_price_yen`・消費量は必ずサーバー／ルール側で入れ、アプリには「表示するだけ」と伝えた
- [ ] `missing`（不足食材）がそのまま買い物リストの入力になることを確認した
- [ ] 失敗時（読めない・異常値）の `errors` の意味を決めた

仮の受け渡しでもよい段階:

- [ ] フォルダに「入力画像 → 出力JSON」のサンプルを5組置く（HTTP APIがまだなくてもアプリ班はモックできる）

## 5. アプリ班との定例連携（週1で十分）

AI班リーダーが数字を持参する。毎回15〜30分。

| 伝えること（AI → アプリ） | 聞くこと（AI ← アプリ） |
|---|---|
| 精度・速度・原価の最新数値 | 画面上で「待たされる」と感じる秒数 |
| JSON（スキャン・提案）の形の変更点 | 「結果にこの項目が欲しい」 |
| 推奨する画像サイズ・画質 | 店内テストで困ったこと（暗い・反射） |
| 名寄せ・換算辞書の更新 | 在庫修正画面で必要な単位の種類 |
| よくある読み取り失敗パターン | ユーザーがやり直したくなる失敗の見せ方 |

- [ ] 初回キックオフ（紙芝居＋JSON合意）を実施した
- [ ] 週次の日付を決めた

## 8. 困ったときの判断ルール

1. **「レコメンドの高度化を先にやりたい」** → 先に値札10枚の精度・秒数・原価と、提案JSONの検証。土台が崩れると全部無駄になる。
2. **「単価・消費量の計算をAIに書かせれば早くない？」** → 書かせない。誤るとユーザーの財布と在庫が嘘になる。ルール＋検算。
3. **「精度が80%で止まっている」** → 失敗パターンを分類（手書き／反射／単位）してからプロンプトや入力画像を変える。いきなり別機能に逃げない。
4. **「何をすればいいか分からない」** → このリストの上から、まだ空欄の `[ ]` を1つ選ぶ。写真が足りなければ撮影に行く。
5. **迷ったら** → `instruction.md` の「ループがつながる」「入力させない」「計算はルール」「§6が最優先」に戻る。
