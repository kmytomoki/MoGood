# B-3 ネットスーパー・生協の注文連携 — 収益構造の詳細

## 0. 結論（先に4点）

1. **同じ導線の前例があり、終了している。** 国内No.1レシピアプリのクラシル（dely）は 2020年12月にイオンリテールと連携し、アプリ内でレシピから食材をネットスーパー注文できる機能を出した。約4万件のレシピを持つ最強の座組だったが、**2023年3月時点でアプリからの注文はできなくなっている**（終了理由は非公開）。MoGood が未ローンチ・ユーザー0 の状態で同じ導線を後追いする根拠は薄い。

2. **ネットスーパー連携は、MoGood の④店頭スキャンと同一ユーザー内で両立しない。** ネットで注文する人は棚の前に立たない。④は「棚の前での購入前判断」を存在意義としている（§2.3）。**B-3 を主軸にすると④が死に、④を主軸にすると B-3 は使われない。** 収益案の中でこれは特殊で、機能そのものと衝突する唯一の案。

3. **ただし生協の紹介だけは切り分けて検討する価値がある。** ASP 経由で**提携交渉なしに今日から始められ**、新規加入1件で約3,000円と単価が高く、生協の利用者像が MoGood の一次ペルソナと重なる。これは B-3 とは別案として扱うべき。

4. **ネットスーパー連携の本当の価値は収益ではなく「入力コストゼロ」である可能性が高い。** 注文データが取れれば購入品目が構造化データで確定し、§2.2 の生命線（ユーザーに入力させない）を完全に解決する。もし将来交渉するなら、**収益条件ではなくデータ連携を目的に交渉すべき。**

## 1. 収益の取り方は2種類ある（性質がまったく違う）

| | **(A) 生協の新規加入紹介** | **(B) ネットスーパーの注文連携** |
|---|---|---|
| 報酬の形 | **一回きりの固定額** | **継続的な料率（注文額の%）** |
| 単価の目安 | 資料請求 約789〜833円 / 新規加入 約3,000円（A8.net の食材宅配プログラム例） | 2〜4%（イオン系は2%前後、楽天系は最大4%。カテゴリにより変動） |
| 開始の難易度 | **低い。** ASP に登録すれば提携交渉不要 | **高い。** 公開APIが見当たらず、個別の業務提携が前提 |
| ストック性 | なし（同じ人からは二度取れない） | **あり**（注文のたびに発生） |
| MoGood との相性 | 献立を先に計画する必要がある層＝一次ペルソナと重なる | ④店頭スキャンと衝突する |

**数値はすべて調査時点の公開情報であり、実際の条件は個別提携で変わる。**

## 2. 単位経済の試算（すべて仮置き）

### 2.1 (A) 生協の新規加入紹介

前提: MAU 1,000人 / そのうち生協未加入かつ加入意向のある層を 3% と仮定 / 年間の実加入率を 1% と仮定

| 項目 | 値 |
|---|---|
| 年間の新規加入 | 1,000人 × 1% = **10件/年** |
| 報酬 | 10件 × 3,000円 = **30,000円/年**（月あたり 2,500円） |
| 比較: サブスク | 480円 × 40人（転換率4%）= **19,200円/月** |

**読み方**: 月あたりの絶対額ではサブスクに遠く及ばない（約13%）。**ただし CAC の観点では意味が変わる。**

> 事業プラン §3.3 の仮置き CAC は 500円/インストール。
> **生協の新規加入1件（3,000円）＝ 新規ユーザー6人分の獲得費用。**
> つまりこれは「収益源」というより**「獲得費用を自前で賄う仕組み」**として効く。

### 2.2 (B) ネットスーパーの注文連携

前提: 週1回・1回8,000円の注文をする世帯 / 料率2〜4%

| 料率 | 月間の報酬（1世帯あたり） | サブスク480円との比 |
|---|---|---|
| 2% | 640円/月 | **1.3倍** |
| 3% | 960円/月 | **2.0倍** |
| 4% | 1,280円/月 | **2.7倍** |

**ARPU としてはサブスクを超える。** 数字だけ見れば最も大きい収益源になりうる。

**ただし前提が4つとも未検証:**
1. MoGood 経由で実際に注文するか（買い物リストを作っても店頭で買うかもしれない）
2. 生鮮食品にその料率が適用されるか（EC のアフィリエイト料率はカテゴリ次第で、生鮮は対象外のことがある）
3. カート連携が技術的に可能か（→ §3-3）
4. そもそも提携できるか（→ §3-4）

## 3. 採用を難しくしている4つの構造問題

### 3.1 クラシル × イオンの前例が終了している（最重要）

| 項目 | 内容 |
|---|---|
| 開始 | 2020年12月、dely（クラシル）× イオンリテール |
| 内容 | アプリ内「スーパー」タブから、約4万件のレシピを見ながら必要な食材をネットスーパーで購入 |
| 現状 | **2023年3月時点でアプリからの注文は不可**（終了理由は公開されていない） |

**国内No.1のレシピ動画アプリが、国内最大級の小売と組んで、3年もたずに畳んだ導線である。** 終了理由は非公開だが、構造的に効きそうな要因は推測できる:

- ネットスーパーは**配送枠と対象エリアの制約**が厳しく、「今日の献立」に間に合わない
- レシピの食材名と、ネットスーパーの実在庫（規格・容量）の**名寄せが難しい**
- レシピ閲覧から注文完了までの**コンバージョンが低い**（見るだけで終わる）

このいずれも MoGood にそのまま当てはまる。**むしろ MoGood は「今日の在庫から今晩の献立」を主戦場にしているため、配送のリードタイム問題はクラシルより深刻。**

### 3.2 ④店頭スキャンと同一ユーザー内で両立しない

`docs/instruction.md` §2.3 は、④の存在意義を「棚の前での購入前の意思決定支援」と定めている。

- ネットスーパーで注文する日 → 店に行かない → ④は使われない
- 店頭で買う日 → ネットスーパーの注文は発生しない → B-3 の報酬はゼロ

**同じユーザーが両方を高頻度で使うことはない。** これは「機能が増える」話ではなく「主戦場をどちらに置くか」という排他的な選択である。他の収益案（A-3・A-5・B-1 など）にはこの性質がない。

### 3.3 外部アプリ向けの公開APIが見当たらない

調べた範囲で、国内の主要ネットスーパー（イオン・楽天西友など）が外部アプリ向けにカート投入や注文のAPIを公開している形跡はない。クラシル×イオンは**個別の業務提携**であって、誰でも使える仕組みではなかった。

ASP（A8.net 等）経由で今できるのは「リンクを送って計測する」までで、**買い物リストをそのままカートへ送る**という B-3 の中身は実現できない。

### 3.4 提携交渉のテーブルにつけない

現状は未ローンチ・ユーザー0・売上0・高校生チーム。イオンや生協が提携を検討する材料が無い。**提携は「ユーザー数」を持ってから初めて交渉材料になる。** 順序が逆。

## 4. 確定事項との関係（重要な区別）

| 文書 | 記述 | B-3 は抵触するか |
|---|---|---|
| `docs/instruction.md` 確定事項8 | 個人利用に徹する（**価格データ**の共有・公開はしない） | **抵触しない。** 注文連携は価格データの共有ではない |
| `docs/instruction.md` 確定事項5 | 店頭比較はその日の棚と個人の購入履歴の範囲のみ | 抵触しない |
| `docs/事業プラン草案.md` §3.1 | 「**小売連携**・価格データ提供は現時点で採らない」 | **抵触する。** B-3 を採るならこの一文の変更が必要 |

つまり **B-3 を阻んでいるのは instruction.md の確定事項ではなく、事業プラン草案の方針記述**である。確定事項の変更（バージョン更新を伴う重い手続き）までは不要で、事業プラン §3.1 の見直しで足りる。ただし §3.1 を変えるなら CEO 承認が要る。

## 5. 推奨（結論）

| 案 | 判断 | 理由 |
|---|---|---|
| **(B) ネットスーパーの注文連携** | **現時点では採らない** | クラシルの前例が終了、④と衝突、API不在、交渉材料なし。**ローンチ後にユーザー数を持ってから、収益ではなく「購入データによる在庫自動入力」を目的に再検討する** |
| **(A) 生協の新規加入紹介** | **切り分けて検討する価値あり（B-3' として別案化）** | ASP 経由で提携不要・単価3,000円・ペルソナが重なる。ただし④とは衝突しない（生協は宅配であり店頭の代替ではなく併用される） |

### 5.1 (A) を採る場合に確認すべきこと

1. 各 ASP（A8.net 等）で実際に募集中のプログラムと現在の単価・承認条件（成果の否認率は高いことがある）
2. 掲載する場所（アプリ内に広告的な導線を置くと `instruction.md` §2 の体験設計を損なう。**「提案の中立性」への影響は B-2 と同じリスク**）
3. 景品表示法・ステマ規制上の表示義務（広告であることの明示）→ legal-agent の確認が要る

### 5.2 (B) を将来検討する場合の交渉材料の作り方

- 交渉に必要なのは「MoGood 経由でどれだけ注文が発生するか」の実績。ローンチ後に**買い物リストの品目数と金額を計測しておく**と、それがそのまま提案資料になる
- ただし④を主戦場に据える限り、この数字は伸びない。**訴求の主軸（`20260819/ターゲット優先順位と訴求軸の整理.md`）とセットで判断すること**
