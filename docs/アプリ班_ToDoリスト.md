# アプリ班 ToDoリスト

対象: 開発経験が少ないメンバー／アプリ班リーダーがサポートしながら進める前提  
参照: `docs/開発プラン.md` / `instruction.md` / `docs/事業プラン草案.md` / `docs/AI班_ToDoリスト.md`

## 0. 班の役割分担（迷ったらここを見る）

| 班 | 担当すること | 担当しないこと |
|---|---|---|
| **AI班** | ラベル・値札の読み取り検証、レシピ提案のプロンプト、単価換算・消費量換算のルール本体、名寄せ・期限カテゴリ辞書 | 画面の見た目・画面遷移・ストア申請 |
| **アプリ班** | 画面設計・スマホアプリ・**在庫→レシピ→買い物リスト→スキャン→修正の導線**・ユーザー体験・（後から）APIとのつなぎ込み | 「AIの中身を自分で作る」「モデルを学習する」「単価・消費量の計算式を発明する」 |

**重要な約束**: AI班の Phase 0（実写ラベルでの精度・速度検証）が終わるまで、アプリ班は「本物のAI連携」に進まない。その間は **画面の紙芝居・モック・環境構築・在庫画面の作り込み** を進める。在庫と買い物リストは AI がなくても作れる——ここがアプリ班の主戦場。

## 1. 今週〜すぐやること（コードを書かなくても進む）

経験ゼロでも着手できる。チェックが全部ついたら「準備完了」。

### A. プロダクトを自分の言葉で説明できる

- [ ] `instruction.md` の §1〜§2 を読む（何を作るか・なぜ「ループがつながる」ことが大事か）
- [ ] 1分で説明できるようにする: 「在庫は自動で管理 → アプリが献立を提案 → 足りない分が買い物リストに → 店では撮るだけでお得判定 → 作ったら在庫が自動で減る → ズレたら簡単修正。これを毎日回す」
- [ ] **やらないこと**を覚える: 完璧な在庫記録をユーザーに強いない／レシート撮影が主役ではない／他の人と価格を共有しない／単価・消費量の計算をAIに任せない

**完了の目安**: 他班の人に口頭で説明して、「ループ」「入力させない」「ズレても直せる」が出てくること。

### B. 参考アプリを触って「型」をメモする

各自スマホで触り、スクショ＋1行メモを共有フォルダ（または Notion / Google Drive）に残す。

| # | アプリ | 見てほしい点 | メモ欄（自分で書く） |
|---|---|---|---|
| 1 | pecco などの冷蔵庫管理系 | 在庫一覧と期限の見せ方。登録が面倒に感じる箇所 | |
| 2 | クラシル | レシピ一覧の見た目。提案カードの情報量 | |
| 3 | Bring! or Google Keep | 買い物リストのチェック操作。片手で使えるか | |
| 4 | Vivino（または類似のラベルスキャン系） | 撮影→待ち→結果の流れ | |
| 5 | Googleレンズ | 枠で「何を読んだか」が分かるか | |
| 6 | マネーフォワード ME（可能なら） | 「自動で貯まっていく感」の画面。手入力なしで台帳ができる体験 | |

- [ ] 上の表を全員が埋めた
- [ ] 班で15分共有: 「MoGoodに真似したい点／真似しない点」を3つずつ出す（特に「登録が面倒」と感じた箇所は宝。うちはそこを消すのが仕事）

### C. 画面の紙芝居（ワイヤー）を作る

ツールは何でもよい（Figma / FigJam / PowerPoint / 手書き写真）。**きれいさより「毎日のループが一周すること」**。

作る画面（MVPのコアループ）:

1. **ホーム** … 今日のレシピ提案カード（「在庫を使い切る」列と「好みのおすすめ」列）+ 期限が近い食材の表示
2. **在庫** … 一覧（期限が近い順）+ 数量を2タップで直せる修正UI
3. **買い物リスト** … レシピから追加された不足食材のリスト。チェックすると「購入した」ことになり在庫に入る
4. **スキャン** … カメラ + シャッター →（解析中）→ お得判定の結果カード
5. **献立確定** … 「この献立で在庫がこれだけ減ります」のプレビュー → 確定ボタン
6. **調理後の修正** … 「実際はもっと使った／余った」を直す画面

- [ ] 紙芝居 v1 を班で1枚の流れにする（1→2→3→4→3→5→6→翌日の1、と指でなぞれること）
- [ ] AI班に見せて「この画面に返すデータの形」のイメージを共有する（連携キックオフ）

**完了の目安**: 紙芝居を指でなぞれば「把握しない・考えない・迷わない・記録しない、でも回る」が一通り説明できる。

## 2. 環境づくり（初めての開発セットアップ）

リーダー（サポート役）が付きっきりでよい。1人で詰まらせない。

### D. ツールのインストール（全員）

- [ ] Git を入れる・GitHub アカウントを作る
- [ ] エディタを入れる（Cursor または VS Code）
- [ ] Node.js（LTS）を入れる ※フロントが Expo の場合
- [ ] 実機 or エミュレータの方針を決める  
  - Android: Expo Go アプリが手軽  
  - iPhone: Expo Go（要 Apple ID）

### E. 「Hello World」まで（班で1リポジトリ）

- [ ] Expo の公式チュートリアルに沿って、空のアプリを実機で起動する
- [ ] 「ボタンを押すと文字が変わる」程度の画面を1つ作る
- [ ] GitHub に push できるところまでやる（ブランチの使い方はリーダーが教える）

**完了の目安**: 自分のスマホで「自分たちが作った画面」が表示される。

> 技術スタックが Flutter に決まった場合は、D/E を Flutter 用に差し替える。**決まるまで Expo で進めてよい**（開発プランの推奨）。

## 3. アプリ班が作るもの（モック → 本物の順）

**在庫と買い物リストはAIなしで作れる**ので、AI班の検証を待たずに本物を作ってよい。スキャンとレシピ提案はダミーJSONから始める。

### F. 在庫画面（Phase 1 の本丸。AIなしで本物が作れる）

- [ ] 在庫一覧（名前・数量・単位・賞味期限、期限が近い順）をローカルデータで表示
- [ ] 食材の追加フォーム（名前・数量・単位。期限は「カテゴリを選ぶと自動で入る」動きをダミー辞書で再現）
- [ ] 数量の修正が**2タップ以内**でできるUI（+/−ボタン or スライダー。`instruction.md` の「ズレ許容+簡単修正」）
- [ ] 初回セットアップ画面のモック（よく使う食材をチェックで一括登録）

**完了の目安**: 自分の冷蔵庫を実際に登録して1週間使ってみて、面倒だった操作をメモできている（これ自体が Phase 0 検証①への貢献になる）。

### G. 買い物リストとレシピ提案のモック（Phase 2 準備）

- [ ] レシピ提案カードを**ダミーJSON**で表示（「在庫を使い切る」「好みのおすすめ」の2列。不足食材がバッジで見える）
- [ ] 「この不足食材をリストへ」ボタン → 買い物リストに追加される動き
- [ ] 買い物リスト画面: チェックすると在庫に追加される動き（ここが**入力自動化の本丸**。オフラインでも動くことを意識）
- [ ] 献立確定画面: 「在庫がこれだけ減ります」の差分プレビュー → 確定で在庫の数字が減る動き（減少量はダミーでよい）

**完了の目安**: AIなしで「毎日のループのデモ」が一周通る（見栄えデモ）。

### H. カメラと画像まわり（本物の撮影）

- [ ] カメラ許可のダイアログを出す
- [ ] 写真を撮って画面にプレビュー表示する
- [ ] 画像を小さく圧縮する（長辺おおよそ1280px・ファイルサイズを意識）※AI班と連携してサイズを決める

### I. AI班とのつなぎ込み（Phase 0 通過後）

AI班から「このURLに画像を送るとJSONが返る」が来てから着手。

- [ ] ダミーJSONを、本物のAPIレスポンス（スキャン・レシピ提案）に差し替える
- [ ] 待ち時間中の表示（スピナー／「読み取り中」）を入れる
- [ ] 失敗時の画面（電波が悪い・読み取れない）を用意する
- [ ] 所要秒数を画面かログに出す（検証の継続計測）

**受け取るデータのイメージ（AI班と事前合意。正式版は AI班ToDo §J）**:

```json
{
  "items": [
    {
      "name": "豚こま切れ",
      "price_yen": 298,
      "quantity_value": 200,
      "quantity_unit": "g",
      "unit_price_yen": 149,
      "basis": "per_100g",
      "is_best_deal": true,
      "vs_my_usual": "cheaper"
    }
  ]
}
```

単価（`unit_price_yen`）と消費量は**アプリ側で計算しない**。AI班／バックエンドのルール計算結果を表示するだけ（`instruction.md` の禁止事項）。

## 5. AI班との定例連携（週1で十分）

アプリ班リーダーが司会。毎回15〜30分。

| 聞くこと（アプリ → AI） | 伝えること（アプリ → AI） |
|---|---|
| 精度・速度・原価の最新数値 | 画面上で「待たされる」と感じる秒数 |
| APIの入出力フォーマット（スキャン・提案）は変わったか | 「結果画面・提案カードでこの項目が欲しい」要望 |
| 画像サイズ・画質の推奨 | 店内テストで困ったこと（暗い・反射など） |
| 期限カテゴリ辞書・換算辞書の更新 | 在庫登録・修正で必要になった単位の種類 |

- [ ] 初回キックオフを実施した（紙芝居＋データ形の合意）
- [ ] 週次の日付を決めた

## 8. 困ったときの判断ルール

1. **「便利そうな機能を足したい」** → まずコアループ（在庫→提案→リスト→確定→修正）が毎日回るかを優先。増やすのは後。
2. **「AIの精度が悪い」** → アプリ班の仕事ではない。画面側は失敗時メッセージを丁寧にする。
3. **「在庫登録が面倒くさい」と感じた** → それは最重要の発見。どの操作が面倒だったかをメモして定例に持っていく（入力コスト最小化が生命線）。
4. **「何をすればいいか分からない」** → このリストの上から、まだ空欄の `[ ]` を1つ選ぶ。
5. **迷ったら** → `instruction.md` の「ループがつながる」「入力させない」「ズレても直せる」「価格は共有しない」に戻る。
