## 1. プロジェクト概要

**プロジェクト名**: life-agent（生活のマルチドメインAI構想）
**本リポジトリ**: 第1弾 = 食品ドメイン（食材管理・献立・買い物支援アプリ）

### 一行で言うと

冷蔵庫の在庫・献立・買い物リスト・店頭でのお得判定・調理後の在庫更新までを1つのループとして管理し、毎日の「把握して・考えて・選ぶ」ストレスをなくす食材管理アプリ。

### 解決する課題（Before）

毎日繰り返される、次の一連の手順のストレス。

1. 冷蔵庫の中をざっと把握して
2. 大体のメニューを考えて、
3. やっと買い物へ。と思ったけど、どのスーパーが安いのか、相場がわからない。
4. お店にて、なるべく安く好みの足りない食材を頑張って選ぶ。面倒な繰り返し。



### 提供する体験（After・確定版）

1. **在庫管理**: 自分で把握しなくても、買った食材はすべてアプリで管理。数量・賞味期限をデータベースで管理する。
2. **レシピ提案**: メニューを考えなくても、アプリが食材を使い切るようにレシピを提案。無理に既存の食材のみで提案せず、ユーザーの**好み寄りのレシピも一緒に**提案できる。
3. **買い物リスト**: 作りたいレシピのうち、足りない食材を買い物リストへ追加。**2日〜5日先の料理も計画に入れて**買い物リストを作成できる。
4. **店頭スキャン**: 気になる食材をラベル込みでスキャンするだけで、どれを買えばお得かすぐに分かる。
5. **消費計算**: これから作るメニューを確定した時点で、使う食材と調味料がどれくらい減るかを計算し、在庫へ反映する。
6. **修正**: 料理後、消費した分量がずれたなと感じても管理画面から簡単に修正できる。1から毎日繰り返す。



### 長期ビジョン

生活の各領域（食品 → 日用品ストック → 家計）を、DB上でAIエージェントに継続管理させる。
本リポジトリで作る基盤（DB + AIエージェント）は第2弾以降へ流用する前提で設計すること。

## 2. 中核となる価値（ここを見失わないこと）



### 2.1 主役は「ループ全体」がつながっていること

冷蔵庫管理・レシピ提案・買い物リスト・単価計算は、**それぞれ単機能のアプリなら既に存在する**。
本アプリの価値は、それらが1つの在庫DBを介して**毎日のサイクルとして一気通貫でつながる**ことにある。

- 在庫が分かるから、レシピが在庫消化型で提案できる
- レシピが決まるから、不足分だけの買い物リストが自動で作れる
- 買い物リストがあるから、購入した瞬間にワンタップで在庫へ反映できる
- 献立を確定するから、消費量を先回りで計算でき、在庫の精度が保たれる

**個々の機能で勝負しない。「つながっていること」が唯一の差別化である。**

### 2.2 入力コストの最小化が生命線

在庫管理アプリ・家計簿アプリが挫折される最大の理由は**手入力の面倒さ**である。
在庫DBの鮮度が落ちた瞬間、レシピ提案も買い物リストも信用を失い、ループ全体が死ぬ。
したがって「ユーザーに入力させない」設計を最優先する。


| 入力が発生する場面  | 自動化の手段                                                 |
| ---------- | ------------------------------------------------------ |
| 購入した食材の登録  | **買い物リスト経由のワンタップ購入確定**（リストにある品はタップだけで在庫へ）＋ スキャンによる読み取り |
| 賞味期限       | カテゴリ別の自動推定を基本とし、傷みやすい商品のみ任意で実測上書き                      |
| 調理による在庫の減少 | 献立確定時に**レシピの分量から自動計算**して引き落とす                          |
| 実際の消費量とのズレ | 事後に管理画面から簡単修正（ズレを許容する設計。完璧な記録を強いない）                    |




### 2.3 店頭では「買う前」に効くこと

店頭スキャン（ステップ4）の存在意義は**購入前の意思決定支援**にある。

- ❌ 買った後に価格が分かっても、その日の選択には効かない
- ✅ 棚の前でラベル込みでスキャン → 共通単価（100gあたり等）に換算 → 買う前にお得が分かる

「効果を出したいタイミング」と「価格が取れるタイミング」を一致させること。
また「どのスーパーが安いのか相場が分からない」という課題には、**個人の購入履歴（台帳）との比較**（いつもより安い/高い）で応える。他ユーザーとの価格共有はしない（§3参照）。

### 2.4 堀（防御力）は技術ではなく蓄積データ

中核技術（ラベルを読む・単価換算・レシピ生成）は汎用AIに乗れば誰でも作れる。技術的参入障壁はほぼない。
したがって防御力は以下に置く:

- **在庫・消費の履歴**: 使うほど「自分の家の回し方」がデータになる（よく作る料理、消費ペース、腐らせがちな食材）
- **個人の買い物台帳**: 「この商品を先週いくら、今日いくら」という利用者固有の値動き履歴
- **好みの実績学習**: 設定入力ではなく実際の選択履歴から価値観を推定（使うほど馴染む = 乗り換えコスト）

**単発の便利機能ではなく、蓄積して効く設計にすること。**

## 3. 確定した設計判断（覆さないこと）

以下は議論の末に確定した。**再提案・蒸し返しをしないこと。**
（v2.0 で改訂した項目には「v2.0改訂」と明記）


| #   | 決定事項                                                | 理由                                             |
| --- | --------------------------------------------------- | ---------------------------------------------- |
| 1   | **アプリの起点は在庫DBを土台にした献立サイクル**（店頭スキャンはその1ステップ）〔v2.0改訂〕 | ユーザーの痛みは店頭の一瞬ではなく、把握→献立→買い物→調理の毎日のループ全体にある     |
| 2   | **在庫への入力は「買い物リスト経由のワンタップ確定」を主軸にし、スキャンで補う**〔v2.0改訂〕  | 手入力を強いると在庫DBの鮮度が保てず、ループ全体が崩壊する（§2.2）           |
| 3   | **レシピ提案は在庫縛りを強制しない**（在庫消化案と好み寄り案を並べて出す）             | 「あるものだけで作れ」は体験として窮屈で、継続利用を損なう。使い切りは提案で誘導する     |
| 4   | **消費量の計算はレシピの分量データからルールベースで行い、事後修正を前提とする**          | 完璧な計量をユーザーに強いない。ズレたら直せる方が現実的で継続する              |
| 5   | **店頭比較は「その日・実際に立ち寄った店の棚」と「個人の購入履歴」の範囲のみ**           | 価格は日々変動するため、他店とのリアルタイム比較や他ユーザーのデータには依存しない      |
| 6   | **賞味期限はカテゴリ別の自動推定を基本とする**                           | 全商品の撮影・入力を強いると入力コストが破綻する。傷みやすい商品のみ任意で実測して上書き   |
| 7   | **基盤モデルは自作しない**（既存VLM/LLM APIを使う）                   | 中核能力は既存APIで十分。自作しても差別化にならない                    |
| 8   | **個人利用に徹する（価格データの共有・公開はしない）**                       | 店舗との摩擦を避ける。クラウドソース型のDB構築は行わない                  |
| 9   | **スマートグラス案は却下**                                     | 普及率・プライバシー・処理コストの3点が逆風。将来の再検討余地は残すが、現時点では対象外   |
| 10  | **レシートOCRを入力の主軸にしない**                               | 下記 §3.1 参照。ただし補助的な購入記録手段としての決済/電子レシート連携は検討余地あり |




### 3.1 レシートOCRの位置づけ（重要な背景）

初期案（v1.0以前）ではレシートOCRを検討したが、「買う前の判断」には原理的に間に合わないため主軸から外した。
v2.0では**購入記録（在庫への反映）の重要性が上がった**ため、次の三段構えとする:

- **在庫への反映（主軸）** → 買い物リスト経由のワンタップ購入確定（買う物は事前にリスト化されているため、最も摩擦が小さい）
- **リスト外の購入・記録の補完** → 店頭スキャン結果からの登録、または決済/電子レシート連携（将来）
- **購入前のお得判定** → 店頭スキャン（この瞬間だけに絞る）

※ POSデータ・レシートに**賞味期限は含まれない**。期限はカテゴリ推定で付与する（確定事項6）。

## 4. 技術方針



### 4.1 AI部分の構成


| タスク                 | 方針                                                                   |
| ------------------- | -------------------------------------------------------------------- |
| ラベル・値札の読み取り         | 汎用マルチモーダルAI（VLM）に画像を投げて構造化データを取得。YOLO等のパターン学習型は食材名の特定に不向き            |
| **単価への換算**          | **ルールベースで確実に計算する（AIに計算させない）**。誤りが価格に直結するため                           |
| **消費量の計算（在庫引き落とし）** | **ルールベース**。レシピの分量 × 人数から決定的に計算する。AIの役割はレシピ食材と在庫アイテムの**名寄せ（マッピング）**のみ |
| 単位のばらつき吸収           | AIに任せる（g表記と枚数表記の混在、「大さじ1」→gの標準換算辞書など）                                |
| 同種商品の判定             | AIに任せる（例: 豚こまと豚バラを混ぜない）                                              |
| 抽出値の検証              | **必ず検算・異常値チェックを挟む**                                                  |
| 賞味期限の推定             | カテゴリ別標準日数の辞書（DB）。AIの役割は品目のカテゴリ分類のみ                                   |
| レシピ提案               | LLMに「在庫（数量・期限）+ 好み設定 + 購買履歴 + 献立計画」を文脈として渡して生成。在庫消化案と好み寄り案を両方出す      |
| 買い物リスト生成            | ルールベース（レシピの必要量 − 在庫量）。名寄せのみAIが補助                                     |




### 4.2 コスト設計

- VLM/LLM API を呼ぶ構造は、ヘビーユーザーほど原価が積み上がる。
- **MVPでは作り込まない**。まず全部API接続で薄く速く作って検証する。
- レシピ提案は毎回生成せず、キャッシュ・提案の作り置きでAPI呼び出し頻度を抑える設計を意識する。
- 将来の最適化: 頻出する定番商品・定番レシピは自前の軽量処理にオフロードし、API課金と速度を同時に改善（二層構成）。



### 4.3 コールドスタート

- 在庫データが空の初期は、初回セットアップ（よく使う食材のチェックリスト一括登録）で最低限の在庫を作る。
- 好みデータが空の初期は、明示的な好み設定 + ルールで動かす。データが貯まるにつれ学習型へ寄せる段階設計とすること。

## 5. MVP機能（実装スコープ）

提供する体験（§1）の6ステップに対応する。

1. **在庫管理**: 食材の数量・賞味期限をDBで管理。一覧・検索・期限順表示。賞味期限はカテゴリ別自動推定（+任意で実測上書き）
2. **レシピ提案**: 在庫を使い切る方向の提案 + ユーザーの好み寄りの提案を並べて表示。期限が近い食材を優先的に消化
3. **買い物リスト**: 作りたいレシピの不足食材をワンタップでリストへ追加。2〜5日分の献立計画からまとめてリスト生成
4. **店頭スキャン**: ラベル込みでスキャン → 商品名・容量・価格を読み取り → 共通単価に換算 → 同じ棚の中でのお得判定 + 自分の購入履歴との比較
5. **消費計算**: 献立確定時に使う食材・調味料の減少量を計算し、在庫へ反映
6. **在庫修正**: 調理後のズレを管理画面から簡単に修正（増減の上書き）



### スコープ外（MVPでは作らない）

- 店舗間のリアルタイム価格比較
- ユーザー投稿型（クラウドソース）の価格共有
- スマートグラス対応
- 自前の画像認識モデルの学習
- 決済/電子レシート連携（将来の補完手段として検討余地のみ残す）
- 栄養管理・カロリー計算（レシピ提案の付加情報程度に留める）

## 6. 最優先で検証すべきこと（他の実装より先）

**この3点が通らなければ、他を作り込んでも土台が崩れる。**

1. **在庫の継続性**: 買い物リスト経由のワンタップ確定 + 消費自動計算 + 事後修正、という入力設計で、**在庫DBの鮮度が2週間維持できるか**（紙のプロトタイプ/簡易アプリでの自己検証でよい）。ここが崩れると全機能が崩れる
2. **スキャンの実用性**: ラベル読み取りのレイテンシ（撮影→判定までの秒数）・精度（商品名・容量・価格の抽出）・1スキャンあたりのAPIコスト
3. **消費計算の妥当性**: レシピ分量→在庫引き落としの計算が、実際の調理とどの程度ズレるか。修正の手間が許容範囲か

**推奨する着手順**: ①を紙 or スプレッドシートで2週間、②を実店舗の値札・ラベル10〜20枚で実測、を並行で始める。
理由: 精度が多少低くても手間が許容内なら製品は成立しうるが、手間が大きいと精度が完璧でも誰も使わない。

**この検証が未了の状態で、レコメンドの高度化や画面の作り込みに進まないこと。**

## 7. 既知のリスク（実装時に意識すること）


| リスク        | 内容                                 | 対応方針                             |
| ---------- | ---------------------------------- | -------------------------------- |
| 在庫DBの鮮度劣化  | 入力・修正が面倒だと在庫が実態と乖離し、ループ全体が信用を失う    | §6-1の検証を最優先。「ズレても直せる」設計で完璧主義を避ける |
| 技術的参入障壁がない | 中核技術は汎用AIで誰でも再現可能                  | 蓄積データ（在庫履歴・台帳・好み学習）を堀にする         |
| 大手に飲み込まれる  | クックパッド・クラシル・チラシアプリが在庫連携を実装すれば模倣可能  | 同上。ループ全体のデータ蓄積による乗り換えコストで守る      |
| スキャンの手間    | 遅い・不正確だと店頭機能の価値がゼロになる              | §6-2の検証を最優先                      |
| APIコスト     | スキャン・レシピ生成とも、使われるほど赤字化しうる          | 頻度削減・キャッシュ + 将来の二層構成             |
| 初期離脱       | 在庫が空の初期は提案の質が低い                    | 初回セットアップの一括登録 + 初回から役立つ体験を設計する   |
| 店舗での撮影許容   | 店が撮影を嫌がる可能性                        | 共有しない個人利用に徹する                    |
| 競合の既存カバー   | 冷蔵庫管理（pecco等）・レシピ提案・買い物リストは単機能では既存 | 単機能で売らず「ループがつながっている」ことで訴求        |
| 収益モデル未確定   | サブスク等の価格受容性が未検証                    | 実装と並行して検証。断定しない                  |

## 8. 開発上の禁止事項

- ❌ **単価・消費量の計算をLLMに丸投げしない**（ルールベース + 検算。AIは読み取りと名寄せのみ）
- ❌ **レシートOCRを入力の主軸にしない**（§3.1の理由）
- ❌ **価格データを他ユーザーと共有・公開する設計にしない**
- ❌ **§6の検証を飛ばして機能を作り込まない**
- ❌ **「便利な単発機能」を増やす方向に流れない**（ループがつながる設計・蓄積して効く設計を優先）
- ❌ **在庫の完全・正確な記録をユーザーに強いる設計にしない**（ズレ許容 + 簡単修正が原則）
- ❌ 基盤モデルの自作・ファインチューニングをMVPで始めない
